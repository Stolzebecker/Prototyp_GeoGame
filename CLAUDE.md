# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

**SCOPE** (Spatial Complexity Observation and Perception Experiment; internal/repo name still "EO Visual Complexity Experiment" — see "Branding" below) — an interactive web experiment for the Research Group for Earth Observation (rgeo). Participants drag labels (Wald/Acker/Gebäude/Wasser) onto the matching regions of a satellite image, or drop them in a trash bin if the feature is absent. Time and errors are recorded per level to study visual complexity perception in remote-sensing imagery.

The **runtime is a static site** (`index.html` + `assets/js/telemetry.js` + `assets/js/app.js` + `assets/js/tutorial.js` + `assets/css/*.css` + `data/config.json` + `Bilder/`), deployed to GitHub Pages. There is no build step and no package manager. There **is** now server-side code — a Google Apps Script backend (`apps-script/Code.gs`, not deployed as part of the static site itself, see "Datenerhebung" below) that the client POSTs to. There is no automated test suite or linter for either the JS or the Python side; verify frontend changes by opening `index.html` in a browser (see "Working with new imagery" for the content-regeneration path). `data/config.json` is generated locally by a separate Python pipeline and must be committed alongside the images.

## Datenerhebung (seit 2026-08-25, Learnings aus dem TIER-List-Projekt übertragen)

**Backend:** `apps-script/Code.gs`, analog zum Vorbild in `03_Projektphasen/02_Empirische Datenerhebung/TIERList/apps-script/Code.gs`, aber mit eigenem Google Sheet + eigenem `SUBMIT_TOKEN`. Acht Tabs, verknüpft über `participant_id`/`lauf_id` (siehe Code.gs-Kommentare für die genaue `resolveRun_`-Logik):
- **Personendaten** — 1 Zeile pro `participant_id`, nur beim allerersten Formular (Platzhalter-Felder: Alter, Bildungsabschluss, Studienfach, GIS-Erfahrung, Geschlecht, Gerät [Computer/Tablet/Handy, seit 2026-08-26 — `geraet`-Spalte per `ensureColumn_()` selbstheilend angehängt, siehe `handlePerson_`], Alias [seit 2026-08-26, siehe "Bestenliste" unten] — Feldliste noch nicht literaturbasiert final).
- **Durchlaeufe** — 1 Zeile pro `lauf_id`, Geräte-/Browser-Metadaten (bewusst OHNE IP/Geolocation/Fingerprinting, siehe Datenschutz-Modal). Zusätzliche Spalte `bekanntheit_status` (seit 2026-08-26, siehe "Familiarity-Check" unten) — per `ensureColumn_()` selbstheilend an das Tab angehängt, statt die Kopfzeile eines bereits live laufenden Sheets fest im Code vorzuschreiben.
- **Level_Ergebnisse** — 1 Zeile pro Level+Label (Zeit, Versuche, Reihenfolge-Position, Fehlwürfe nach Ziel getrennt).
- **Drop_Versuche** — 1 Zeile pro Ablage-Versuch (auch Fehlversuche), inkl. `x_frac`/`y_frac`-Ablageposition und der am Ort tatsächlich laut GeoJSON vorhandenen Klasse(n) — ermöglicht räumliche Auswertung typischer Fehlzuordnungen.
- **Bildwiedererkennung** (seit 2026-08-26) — 1 Zeile pro vom Probanden als bekannt markiertem/benanntem Bild (`level`, `region_name`). Leer für alle, die nichts markieren. Siehe "Familiarity-Check" unten.
- **Feedback** (seit 2026-08-26) — 1 Zeile pro abgesendetem Freitext-Feedback aus dem Abschlusspopup.
- **Bestenliste** (seit 2026-08-26) — 1 Zeile pro Durchlauf (`alias`, `total_time_ms`, `total_errors`, `disqualifiziert`). Siehe "Bestenliste/Alias" unten.

**Bestenliste/Alias (seit 2026-08-26, umgebaut 2026-09-02, siehe Memory `project_geogame_structured_alias` für die vollständige Entscheidungshistorie):** Der Alias wird **nicht mehr frei getippt** (das ursprüngliche `#pf-alias`-Textfeld gab es bis 2026-09-02, kein Profanity-Filter, daher ersetzt). Stattdessen zeigt `tutorial.js` nach dem Personendaten-Formular einen eigenen Bildschirm (`showAliasPickerScreen()`): drei Wortpool-„Räder" im Stil der iOS-Wecker-/Timer-Auswahlwalzen (neutrales Adjektiv / geografisches Adjektiv / geografisches Subjekt, siehe `data/alias_words.json` — je 50 Einträge pro Kategorie und Sprache, Herkunfts-Prompt fürs Nachgenerieren/Erweitern siehe Abschnitt „Alias-Wortlisten generieren" unten). Pro Kategorie werden bei Bildschirmaufbau **5 zufällige Wörter** angeboten (`pickRandomN_()`), durch die per Scroll-Snap (`scroll-snap-type:y mandatory`, kein Freitext, kein Reroll) geblättert wird; die Mitte markieren zwei dünne Linien (`.alias-wheel-highlight`, an `top:50%`+`transform:translateY(-50%)` verankert, nicht an einem festen Pixel-Offset — das war ein realer Bug in der ersten Fassung, siehe unten). Wörter verblassen/verkleinern sich mit Abstand zur Mitte (`dist-0`/`dist-1`-Klassen, gesetzt in `updateAliasSelectedClasses_()`), zusätzlich ein CSS-Farbverlauf an den Rädern oben/unten. **Deutsch bekommt einen Artikel nach dem grammatischen Geschlecht des gewählten Substantivs** (`genus`-Feld je DE-Subjekt-Eintrag: der/die/das — NICHT das persönliche `geschlecht`-Feld aus dem Formular, das ist unabhängig davon), Englisch immer `The` (kein Genus im Englischen). Der Genus wird nur im zusammengesetzten Vorschau-String gezeigt, nicht zusätzlich im Rad-Eintrag selbst (Julians ausdrücklicher Wunsch — ein erster Entwurf zeigte ihn testweise auch im Rad, wirkte redundant). Pflichtfeld, kein Freitext-Fallback. `onAliasPickerContinue()` ruft danach ganz normal `submitPersonData(fields)` mit dem fertigen String auf — `getAlias()`/`setAlias()`/die `localStorage`-Persistenz (`geogame_alias`) in `telemetry.js` sind dabei komplett unverändert geblieben, nur die Erzeugung des Werts hat sich geändert. Fällt beim Absenden auf `participant_id` zurück, wenn aus irgendeinem Grund kein Alias vorliegt (schon anonym) — in der Praxis kommt das seit der Pflichtfeld-Umstellung nicht mehr vor.

**Bug in der ersten Fassung des Auswahlrads (gefunden von Julian noch in derselben Session):** die ursprüngliche Optik hatte Auf/Ab-Pfeiltasten pro Rad und eine gelb gefüllte Markierungsbox bei einem festen `top:48px`-Offset — der Offset ignorierte, dass die Pfeiltasten selbst Platz im Container einnahmen, wodurch die Box sichtbar zu weit oben lag statt genau auf Höhe des zentrierten Worts. Behoben durch (a) Entfernen der Pfeiltasten komplett (näher an der gewünschten iOS-Wecker-Optik, reines Scroll/Swipe wie beim Vorbild), was den Container auf die reine Radhöhe reduziert, und (b) prozentuale Zentrierung (`top:50%`+`translateY(-50%)`) statt eines von Hand berechneten Pixelwerts — dadurch ist die Markierung robust gegen jede künftige Änderung an Radhöhe/Itemzahl, statt bei jeder Anpassung neu von Hand nachgerechnet werden zu müssen.

### Alias-Wortlisten generieren/erweitern (`data/alias_words.json`)

Die 6 Wortlisten (DE/EN × neutral/geo-Adjektiv/geo-Subjekt, je 50 Einträge) wurden nicht von Claude frei erfunden, sondern über folgenden Prompt in einer anderen KI generiert, von Julian manuell in einer Excel-Tabelle geprüft/redigiert und dann von Claude in `data/alias_words.json` übernommen. Bei Bedarf (Erweiterung, neue Sprache, Pool zu klein) denselben Prompt wiederverwenden bzw. anpassen:

```
Ich baue ein Lernspiel für Schüler:innen zum Thema Fernerkundung/Satellitenbilder
(Landschaftserkennung, Bildkomplexität). Ich brauche kuratierte Wortlisten für einen
spielerischen Alias-Generator (Vorbild: der Namensgenerator aus "Super Auto Pets"),
der einen fertigen Spitznamen aus fest vorgegebenen Bausteinen zusammensetzt -
KEIN Freitext, nur Auswahl aus Listen.

Zielformat des fertigen Alias:
- Deutsch: "Der/Die/Das [neutrales Adjektiv] [geographiespezifisches Adjektiv] [geographiespezifisches Substantiv]"
  Beispiel: "Der Super Steinige Regenschauer"
- Englisch: "The [neutral adjective] [geography-specific adjective] [geography-specific noun]"
  Beispiel: "The Super Rocky Rainshower"

Erstelle sechs Wortlisten mit je 50 Einträgen (keine Duplikate innerhalb einer Liste):

1. DEUTSCH - neutrales, fachfremdes, positives/lustiges Adjektiv
   (z.B. Super, Riesig, Schlau, Wild, Flink).
   WICHTIG: Gib jedes Adjektiv bereits in der grammatisch korrekten Form für
   "Der/Die/Das ___e ..." im Nominativ Singular an (diese Endung "-e" ist bei
   bestimmtem Artikel für alle drei Genera identisch) - also "Riesige" statt
   "Riesig", "Schlaue" statt "Schlau". Achte auf unregelmäßige Formen
   (z.B. "Hohe" statt "Hoche", "Dunkle" statt "Dunkele").

2. DEUTSCH - geographiespezifisches Adjektiv, thematisch passend zu
   Fernerkundung/Satellitenbildern/Landschaftsformen
   (z.B. Steinig, Hochaufgelöst, Klimatisch, Bewaldet, Multispektral, Pixelig).
   Gleiche grammatische Regel wie oben: bereits im "-e"-Nominativ dekliniert.

3. DEUTSCH - geographiespezifisches Substantiv
   (z.B. Regenschauer, Satellit, Gletscher, Düne, Tal, Wolke).
   Gib zu JEDEM Wort das grammatische Geschlecht an (der/die/das), da der
   Artikel im fertigen Alias davon abhängt. Format: "Wort (der/die/das)".

4. ENGLISCH - neutral, generic, positive/funny adjective, not geography-specific
   (e.g. Super, Giant, Clever, Wild, Swift).

5. ENGLISCH - geography-specific adjective, thematically fitting remote sensing/
   satellite imagery/landscapes (e.g. Rocky, High-Res, Climatic, Forested,
   Multispectral, Pixelated).

6. ENGLISCH - geography-specific noun
   (e.g. Satellite, Glacier, Rainshower, Dune, Valley, Cloud).

Weitere Vorgaben:
- Zielgruppe: Schüler:innen (Sekundarstufe) - Wortschatz altersgerecht und
  schulisch verständlich halten, keine anstößigen, vulgären oder
  zweideutigen Begriffe, keine Wortkombination soll bei zufälliger
  Zusammensetzung unangemessen wirken können.
- Maximal ca. 14 Zeichen pro Wort (wird auf kleinen Mobile-Bildschirmen in
  einem Scroll-Rad angezeigt, muss kurz bleiben).
- Keine Dopplungen innerhalb einer Liste.
- Gib die Ausgabe als sechs klar getrennte, nummerierte Tabellen aus
  (Spalten: "Wort", bei Liste 3 zusätzlich "Genus"), damit ich sie 1:1
  in Excel einfügen kann.
```

`data/alias_words.json`-Struktur: `{"de": {"neutral": [...50 Strings...], "geoAdj": [...50 Strings...], "geoNoun": [{"wort":"...","genus":"der|die|das"}, ...50]}, "en": {"neutral":[...], "geoAdj":[...], "geoNoun": [...50 Strings...]}}`. Alle Wörter sind bewusst durchgängig großgeschrieben (auch deutsche Adjektive, die normalerweise klein geschrieben würden) — der zusammengesetzte Alias wird wie ein generierter Eigenname behandelt, nicht wie normaler Satztext.

`showResults()` schickt einmalig `submitRunSummary(totalTimeMs, totalErrors)` (Werte, die für die bestehende GESAMT-Zeile ohnehin schon berechnet werden) → `handleRunSummary_` in Code.gs setzt `disqualifiziert = totalErrors > DISQUALIFY_ERROR_THRESHOLD` (10 seit 2026-08-27, ursprünglich 5 — siehe dieselbe Konstante `DISQUALIFY_ERROR_THRESHOLD` in app.js). Julians bewusste Entscheidung: **kein separates Opt-in** für die Bestenliste — stattdessen wurde die bestehende "arbeite natürlich, nicht extra schnell"-Instruktion um den Hinweis ergänzt, dass auch Genauigkeit zählt (>10 Fehler = Ausschluss von der Bestenliste), und die Datenschutzerklärung/Consent-Texte wurden um die Offenlegung erweitert, dass Alias+Zeit für andere Teilnehmende sichtbar sind. Faire Vergleichbarkeit der rohen Gesamtzeit trotz zufälliger 8-von-60-Bildauswahl war explizit **kein** Ziel ("nicht schlimm, wie bei vielen Spielen").

Lesezugriff auf die Bestenliste läuft über einen **dritten, öffentlichen Token** `LEADERBOARD_TOKEN` (in `telemetry.js` und `Code.gs`, getrennt vom privaten `READ_TOKEN`) — `doGet(e)` mit `?mode=leaderboard&token=...` liefert NUR aggregierte Werte (Top-10/volle Liste mit Alias+Zeit+Fehlern, eigene Platzierung, Perzentile pro angefragtem Level), nie rohe Personendaten. Bewusst als **GET** (nicht `doPost`) implementiert, weil einfache GET-Requests keinen CORS-Preflight auslösen und die Antwort — anders als die no-cors-POSTs für alle anderen Submissions — tatsächlich lesbar ist; dieses Muster war schon fürs Auswertungs-Dashboard erprobt (siehe [[reference_geogame_dashboard]]) und wurde 2026-08-26 zusätzlich direkt per Browser-`fetch()` gegen die echte Web-App-URL verifiziert (Response kommt lesbar zurück, kein CORS-Block). `telemetry.js`s `fetchLeaderboard(levelTimes)`/`fetchLeaderboardFull()` übergeben `participantId`+`runToken`, damit der Server über `resolveRun_()` dieselbe `lauf_id` wiederfindet, die der Client wegen der no-cors-Submissions sonst nie erfährt. Eigene Platzierung wird immer separat angezeigt (auch außerhalb der Top 10); Dedupe fürs "bester Lauf pro Person" läuft über `participant_id`, nicht über den Alias-String (Aliase sind nicht eindeutig). Perzentile pro Bild werden aus `Level_Ergebnisse` berechnet (`max(gesamtzeit_ms)` je Lauf+Level, siehe [[reference_geogame_dashboard]] für dieselbe Aggregationslogik), keine redundante Extra-Speicherung. **Ladezeit:** Apps-Script-Requests haben spürbare Latenz (Cold-Start + Sheet-Scan, oft 1-3s) — nicht wegoptimierbar, deshalb zeigt `loadLeaderboard_()` seit 2026-08-26 explizit "Bestenliste wird geladen …"/"Lädt …" statt stillschweigend zu warten (wirkte davor wie ein Fehler, Julians Testfund).

**"Freund*in herausfordern" (seit 2026-08-26):** `shareChallenge()` in app.js versucht zuerst `navigator.share()` (native Share-Sheet auf Mobilgeräten — Instagram/TikTok tauchen dort automatisch mit auf, das übernimmt das Betriebssystem); nur wenn die API fehlt (die meisten Desktop-Browser), öffnet `openShareFallbackModal_()` ein Modal mit fünf Plattform-Buttons statt einer reinen Zwischenablage-Kopie — Julians ausdrückliche Wahl. WhatsApp (`wa.me/?text=`), X/Twitter (Intent-URL) und `mailto:` unterstützen echte vorausgefüllte Share-Links — bei WhatsApp öffnet das nicht nur WhatsApp Web, sondern direkt die Kontaktauswahl mit bereits eingetipptem Text (deshalb bewusst **kein** `copyThenOpen_()` für WhatsApp, siehe "WhatsApp-Emoji-Bug" unten für die Zwischenstation, die das kurz ersetzt hatte). Instagram/TikTok bieten das für Web-Seiten **nicht** (kein öffentliches Share-Intent für Text+Link) — dafür kopiert `copyThenOpen_()` den Text in die Zwischenablage (mit sichtbarem Hinweis) und öffnet die Plattform in einem neuen Tab, statt einen funktionslosen Button vorzutäuschen. **CSS-Falle:** `.legal-modal-card button{...}` (generische Regel für alle `<button>` im Legal-Modal-Stil) hat höhere Spezifität als eine einzelne `.share-platform-btn`-Klasse — die Instagram/TikTok-`<button>`-Elemente sahen deshalb anders aus als die WhatsApp/Twitter/E-Mail-`<a>`-Elemente, bis der Selektor auf `.share-platform-row .share-platform-btn` (zwei Klassen) verschärft wurde. Nachrichtentext (`buildShareText_(whatsapp)`, DE **und EN** je nach `tutLang`) nennt den eigenen Bestwert nur, wenn `_lastMyRank` gesetzt ist (aus dem letzten erfolgreichen `loadLeaderboard_()`-Abruf, also ein echter, nicht disqualifizierter Bestwert) — sonst bewusst generische Nachricht ohne Zahl, statt den Button zu verstecken (ebenfalls Julians Entscheidung). Zwei Absätze: persönliche Ansprache + ein zweiter Absatz mit Studien-/rgeo-Kontext (Fakten decken sich mit `TUT_TEXTS.consentBody` in tutorial.js), damit die Nachricht seriöser wirkt statt wie eine reine Spiele-Einladung. Ziel-URL ist `location.origin + location.pathname` zur Laufzeit, kein hartkodierter Wert (die Live-URL läuft überraschenderweise direkt auf der Root-Domain `https://stolzebecker.github.io`, nicht unter einem Projekt-Unterpfad wie bei TIER-List).

**Formatierung/Emojis (seit 2026-08-26):** Emojis funktionieren kanalübergreifend problemlos (reines Unicode) — **außer über WhatsApps eigenen `wa.me/?text=`-Link**, dort lässt `buildShareText_(true)` sie deshalb bewusst weg (siehe "WhatsApp-Emoji-Bug" unten). Fett/kursiv nur über WhatsApps eigene `*fett*`/`_kursiv_`-Textsyntax — die rendert **ausschließlich bei WhatsApp**; überall sonst (Twitter, `mailto:`, natives Share-Sheet, Instagram/TikTok-Kopie) blieben die Sternchen/Unterstriche als literale Zeichen sichtbar, deshalb erzeugt `buildShareText_(true)` nur für den WhatsApp-Link eine gesondert formatierte Variante. Echtes Unterstreichen gibt es in keinem der Kanäle als reiner Text — technisch nicht möglich, nicht umgesetzt.

**WhatsApp-Emoji-Bug (gefunden + diagnostiziert 2026-08-26, Julians eigener Live-Test):** Der `wa.me/?text=...`/`api.whatsapp.com`-Link zeigt Emojis als "�" an; direkt reproduziert durch Navigieren zur offiziellen `wa.me`-Vorschau-Seite mit einer nachweislich korrekt UTF-8-/`encodeURIComponent`-kodierten URL — **selbst einfache Einzel-Codepoint-Emojis ohne Variation-Selector** (👋💪🔬🙏) korrumpieren dort, nicht nur die zusammengesetzten (⏱️🛰️); `*fett*`/`_kursiv_`-Markdown und Umlaute sind im selben Link dagegen unbeschädigt. Julian kopierte denselben Text testweise per Strg+C/Strg+V direkt in die WhatsApp-App (ohne den `?text=`-Umweg) — dort erschienen alle Emojis fehlerfrei, was zeigt: der Bug sitzt konkret in der `?text=`-Vorschauseite, nicht in WhatsApps Emoji-Rendering allgemein. **Erster Fix-Versuch (kurzzeitig, seither wieder verworfen):** WhatsApp-Button auf `copyThenOpen_()` umgestellt (Text kopieren + `web.whatsapp.com` öffnen) wie bei Instagram/TikTok — technisch emoji-sicher, aber Julian bemängelte den echten UX-Verlust: er landet zwar eingeloggt auf der Chat-Liste, aber **ohne** die von `wa.me/?text=` sonst automatisch geöffnete Kontaktauswahl mit bereits eingetipptem Text; er müsste jeden Chat manuell suchen und einfügen. **Endgültiger Fix:** zurück zu `<a href="https://wa.me/?text=...">` (kein `copyThenOpen_()` mehr für WhatsApp) — aber `buildShareText_(true)` lässt jetzt gezielt nur die Emojis weg (Parameter-Objekt `e.wave`/`e.sat`/etc., leer wenn `whatsapp===true`) und behält `*fett*`/`_kursiv_`. Ergebnis: die Kontaktauswahl mit vorausgefülltem Text funktioniert wieder wie ursprünglich gewollt, nur ohne Emojis speziell im WhatsApp-Text — klar der bessere Kompromiss als der Funktionsverlust der Kontaktauswahl. Instagram/TikTok bleiben beim `copyThenOpen_()`-Ablauf, da sie ohnehin nie ein echtes Share-Intent hatten (siehe oben). Deren Ziel-URLs wurden bei dieser Gelegenheit auch korrigiert: **Instagram** `instagram.com/` landete auf Feed/Login statt Postfach → jetzt `instagram.com/direct/inbox/` (offiziell dokumentierte Desktop-Web-DM-Inbox-URL). **TikTok** `/upload` öffnete den Video-Hochlade-Flow, hat mit Nachrichten senden gar nichts zu tun → jetzt die reine Startseite `tiktok.com/` (Nachrichten-Icon sitzt dort in der Seitenleiste; TikTok hat anders als Instagram keine öffentlich dokumentierte Direct-Message-Inbox-URL, ein geratener `/messages`-Pfad wäre nicht verifiziert gewesen). Twitter/X (`intent/tweet`) und `mailto:` wurden ebenfalls gegengeprüft und funktionieren wie vorgesehen (X bewahrt das Compose-Ziel sogar über einen Login-Redirect via `redirect_after_login=`). Statt einer "nackten" URL sorgen Open-Graph-/Twitter-Card-Metatags im `<head>` (`og:title`/`og:description`/`og:image`/`twitter:card`) dafür, dass WhatsApp/X/iMessage/Slack/Facebook automatisch eine Vorschaukarte zeigen, sobald der Link geteilt wird (die URL selbst muss trotzdem im Text stehen, damit Plattformen sie erkennen — es gibt keinen Weg, in reinem Text ein anklickbares Wort statt der URL anzuzeigen). `mailto:`/Instagram/TikTok können so eine Karte nicht darstellen, dort wird der Link stattdessen mit einem Hinweistext ("👉 Hier geht's zum Spiel:") eingerahmt.

**Familiarity-Check (seit 2026-08-26):** Nach dem letzten Level (vor dem Abschlusspopup) fragt `#familiarity-modal` ("Kannten Sie eine oder mehrere der gezeigten Landschaften bereits?"). "Nein" → Status `nein`, direkt weiter zum Abschlusspopup. "Ja" → `#familiarity-gallery-screen` zeigt alle in `results` gesammelten Bilder dieses Durchlaufs als Grid; pro Bild ein Lupen-Button (öffnet den bestehenden `openImagePreview()`-Zoom/Pan-Lightbox wieder, keine eigene Implementierung) und ein Haken-Button (öffnet `#familiarity-name-modal` zum Eintippen der Region/des Orts — erneutes Anklicken eines bereits markierten Bildes öffnet das Popup vorausgefüllt mit "Markierung entfernen"-Option; "Abbrechen" verwirft die Eingabe folgenlos). Alle Markierungen bleiben rein clientseitig (`familiarityMarks` in app.js), bis "Fertig ›" geklickt wird — erst dann sendet `submitFamiliarity()` (telemetry.js) einmalig den finalen Stand. Serverseitig (`handleFamiliarity_` in Code.gs) überschreibt das den bei `handleLauf_` gesetzten Default `bekanntheit_status = "abgebrochen"` mit `"ja"`/`"nein"` (Zeilen-Update per `lauf_id`-Suche unter `LockService`-Lock) — der Default bleibt unverändert stehen, wenn ein Durchlauf vor Erreichen der Frage abgebrochen wurde, sodass die Spalte alle drei Fälle ("ja"/"nein"/"abgebrochen") sauber unterscheidet (Julians ausdrücklicher Wunsch, siehe Grilling-Runde 2026-08-26). `debugJumpToResults()` (QA-Shortcut, Taste `D`) umgeht den Familiarity-Check bewusst und springt direkt zu `showResults()`.

**Interviewmodus & App-Version (seit 2026-09-01, siehe Memory `project_paper1_pivot_no_tierlist`):** Hintergrund: Julian hat die TIER-List-Pilotstudie zugunsten des echten GeoGame verworfen; die Interview-Leitfaden-Übung wird stattdessen zu einer echten Concurrent-Think-Aloud-Übung ausgebaut (Interviewte spielen echte Level, während sie ihre wahrgenommene Bild-Komplexität verbalisieren). Zwei neue, unabhängige Mechanismen dafür:

## Real-imagery sourcing (current, since 2026-08-26)

GeoGame's images are now sourced the same way as TIER-List's: real true-color Sentinel-2 L2A imagery via the shared Copernicus Data Space Ecosystem pipeline at `03_Projektphasen/02_Empirische Datenerhebung/Satellitenbilder/` (outside this repo). That pipeline now has a **`--profile game`** option (added 2026-08-26, alongside the pre-existing `pilot` profile used for TIER-List) producing 4:3 images at **7000×5250 m / 700×525 px** (fixed gain/gamma, identical rendering params to TIER-List) — its own `config.py` constants (`GAME_EXTENT_METERS_W/H`, `GAME_IMAGE_SIZE_PX_W/H`), own metadata CSV (`data/metadata/bildpool_game.csv`, kept separate from TIER-List's `bildpool.csv` since it already has a fixed, incompatible header) and own output folders (`data/tif_game/`, `data/jpg_game/`, both gitignored). Full parameter/decision record: Memory `project_geogame_real_imagery`.

Two-stage workflow to grow/refresh the pool:
1. **Acquire raw candidates** (in the Satellitenbilder repo): `python scripts/pipeline.py --n <count> --profile game` — pulls true-color TIFs, auto-rejecting cloudy/nodata candidates and redrawing until `<count>` succeed (see that repo's own docs for cloud/season/region constraints, identical to the pilot profile).
2. **Classify + filter into GeoGame** (in this repo): copy the new TIFs from the Satellitenbilder repo's `data/tif_game/` into this repo's `input/`, then `python scripts/build_real_pool.py --input-dir input`. This is a **new script**, not the old GUI `pipeline.py` — it reuses `pipeline.py`'s OSM/WorldCover helper functions but differs in three ways: (a) **no percentile-stretch** — the source TIFs already have a fixed gain/gamma true-color render baked in by the Satellitenbilder pipeline, so only crop+resize happens, applying a second adaptive per-image stretch on top would reintroduce exactly the rendering-as-confound problem the fixed gain/gamma was designed to avoid; (b) a **category-coverage filter**: a candidate is only kept if **at least 2 of the 4 classes have area fraction ≥ `AREA_THRESHOLD`** (clearly visible, not just technically present) — rejected candidates have their PNG/GeoJSON deleted and are not added to `config.json` (this is a GeoGame-specific rule, TIER-List has no such requirement, and Fortschrittsdokumentation_Bildakquise.docx Abschnitt 7.2 had actually rejected this exact requirement in an earlier planning pass for the *shared* pool concept that predates the 4:3 split — the rule is intentionally reinstated for GeoGame only); (c) level **id is the Satellitenbilder candidate id itself** (e.g. `IMG_00001`) instead of a sequential `B<n>` — makes the script idempotent/incrementally re-runnable (already-processed TIFs are skipped by id, `config.json` is saved after every accepted level so an interrupted run loses nothing, `B1`'s tutorial entry is never touched since nothing will ever produce that id again).

The **old GUI pipeline (`pipeline.py` via `Verarbeitung_starten.bat`/`.exe`) is legacy** — it's what generated the original false-color image set (now fully removed) and still works exactly as before if ever needed again, but is no longer the primary content workflow. Its percentile-stretch behavior is specifically wrong for the new pre-rendered true-color source TIFs — don't point it at Satellitenbilder-sourced TIFs without the same fix `build_real_pool.py` applies.

## Content pipeline (legacy, local only, never runs on GitHub Pages)

Kept for reference / in case the old false-color workflow is ever needed again. Two ways to (re)generate game content from source satellite imagery the old way:

**A. GUI pipeline (current, preferred)** — `pipeline.py`, a Tkinter app launched via `Verarbeitung_starten.bat` (or the prebuilt `Verarbeitung_starten.exe`). Fully automated end-to-end:
1. Reads every TIF in `input/` (deduplicated by normalized path).
2. Center-crops each to 4:3 and resizes to 1024×768, normalizing bands via 2nd/98th percentile stretch → writes `Bilder/EO_Bilder/B{n}norm.png`.
3. Derives the image's WGS84 bounding box from the TIF's CRS/transform.
4. Queries OSM Overpass API per label class (`OSM_CLASSES` dict — separate filters for Wald/Acker/Gebäude/Wasser, with line-buffering for rivers) against that bbox, falling over three mirror endpoints on failure/rate-limit. A full request failure (not just an empty result) aborts that level entirely rather than silently writing a false "absent" flag — see `run_pipeline`'s try/except around the OSM loop.
5. Converts results to shapely geometries, reprojects to an estimated UTM CRS for buffering, dissolves per class, clips to the image bounds, and writes `Bilder/Hitboxes/B{n}puf.geojson`.
6. **WorldCover gap-fill + cross-check**: OSM is the preferred/higher-resolution source, but it's inherently incomplete (only contains what volunteers mapped). `fetch_worldcover_window()` streams the matching ESA WorldCover 10m tile (public S3, no auth, COG via `/vsicurl/`) for the level's bbox and reclassifies it via `WORLDCOVER_RECLASS`. For each class, any WorldCover-classified area not already claimed by *any* OSM class is added as a gap-filler polygon (never overwrites an existing OSM classification); OSM polygons are also cross-checked against the WorldCover majority class underneath them, logging a warning (not an auto-correction — OSM stays authoritative) when they disagree by more than `WORLDCOVER_CONTRADICTION_THRESHOLD`. A side effect: class polygons can now overlap slightly at their edges (a WorldCover gap-fill sliver next to an OSM polygon of a different class, or two OSM polygons that were never mutually exclusive) — code that hit-tests a drop point must not assume at most one class matches (see `handleStageDrop`/`tutPracticeCheck` below).
7. Computes each class's area fraction of the image (Web Mercator shoelace formula, subtracting polygon holes — see `polygon_area_m2`) and writes `data/config.json` directly — no separate config-generation step needed.

Rebuild the `.exe` with:
```bash
build_exe.bat
```
(runs `pip install rasterio numpy pillow requests geopandas shapely pyinstaller` then PyInstaller with `Verarbeitung_starten.spec`.)

**B. Manual two-script pipeline (older, still present)** — used when hitboxes are hand-drawn/sourced some other way rather than pulled from OSM:
```bash
pip install rasterio numpy pillow
python scripts/convert_tif_to_png.py   # Bilder/EO_Bilder/B*norm.tif → B*norm.png
python scripts/generate_config.py      # reads TIF bounds + GeoJSON "klasse" properties → data/config.json
```
Both pipelines share the same area-threshold logic and the same `ALL_LABELS` id list (`Wald, Acker, Gebäude, Wasser`) — keep them in sync if labels change. Note: `scripts/generate_config.py` has no OSM/WorldCover logic of its own — it just reads pre-tagged GeoJSON `"klasse"` properties, so it only needs the label list itself kept in sync, not the hybrid classification approach. There's also a superseded, standalone `Convert tif to png.py` at the repo root (older duplicate of `scripts/convert_tif_to_png.py`) — not part of either documented pipeline, don't edit it by mistake.

### `data/config.json` shape

```json
{
  "labels": [{"id","text","icon"}, ...],
  "area_threshold": 0.05,
  "levels": [
    {
      "id": "B1",
      "imgSrc": "./Bilder/EO_Bilder/B1norm.png",
      "geojsonSrc": "./Bilder/Hitboxes/B1puf.geojson",
      "bounds": [[southLat, westLon], [northLat, eastLon]],
      "absent": ["Wasser"],
      "absent_optional": ["Gebäude"],
      "areas": {"Wald": 0.42, "Gebäude": 0.18, ...}
    }
  ]
}
```
- `absent`: class has zero area in the image → only the trash bin is a correct drop.
- `absent_optional`: class area is below `area_threshold` (default 5% of image area) → **both** the trash bin and the map hit-zone count as correct.
- `areas`: per-class area fraction (0–1), used only for the debug panel display.
- Area threshold is defined independently in `pipeline.py` (`AREA_THRESHOLD`) and `scripts/generate_config.py` (`AREA_THRESHOLD`) — change both if adjusting.
- `bounds` is WGS84 (`[[southLat, westLon], [northLat, eastLon]]`) and is informational only (e.g. dashboard display) — it is **not** used to place hitboxes anymore. The referenced GeoJSON's own coordinates are already `[fracX, fracY]` in `[0,1]×[0,1]` image-pixel space (see the frontend architecture note below and `pipeline.py`'s `wgs84_geom_to_pixel_fraction`).

Committed to the repo: generated **PNGs**, **GeoJSONs**, **config.json** (for GitHub Pages) — but also, perhaps surprisingly, the raw source **TIFs in `input/`**, and the PyInstaller **build artifacts** (`build/`, `dist/`, `Verarbeitung_starten.exe`). Only `Bilder/EO_Bilder/*.tif` is gitignored; nothing under `input/` is. Keep this in mind before assuming a "raw data stays local" convention applies repo-wide.

## Frontend architecture (`assets/js/app.js`, `assets/js/tutorial.js`)

Two plain-script globals, no modules/bundler, loaded directly by `index.html` in this order: `app.js` then `tutorial.js` (tutorial.js reads/calls globals defined in app.js: `CONFIG`, `buildZones`, `renderLabels`, `ensureMouseEvents`, `loadLevel`, `startShuffledExperiment`).

**Flow:** `boot()` (on `DOMContentLoaded`) fetches `data/config.json` → shows start screen → `startTutorial()` (tutorial.js) drives language selection → 3 info screens → 4-step spotlight overlay tutorial → one practice round (must correctly drop "Wasser") → `finishTutorial()`/`skipTutorial()` calls `startShuffledExperiment()` to begin the real experiment.

**Real imagery + pool model (since 2026-08-26):** GeoGame switched from synthetic false-color images to real true-color Sentinel-2 imagery, and from a small curated level set to a large pool with random per-session sampling — see "Real-imagery sourcing" below and Memory `project_geogame_real_imagery` for the full decision record. `data/config.json`'s `levels` array now holds the **entire pool** (`B1` tutorial + target 60 real `IMG_*` levels), not just what's shown in one playthrough. (The intermediate step of trimming to 9 false-color levels B1–B9 on 2026-08-26 was superseded the same day by the real-imagery switch — B2–B9 and their assets no longer exist.)

**Randomised level order + per-session pool sampling:** `buildLevelOrder()` first Fisher-Yates-shuffles indices `1..N-1` (index `0` = tutorial, excluded), then slices to `LEVELS_PER_SESSION` (8) — mathematically equivalent to drawing a random 8-subset in random order. This runs fresh on every app start/reload with **no cross-session memory** (a deliberate choice — repeat players can by chance see overlapping sets, matches the existing "repeated play is intended" design premise). `levelOrder` holds only those 8 indices; `orderPos` tracks position within them. `nextLevel()` increments `orderPos` and loads `levelOrder[orderPos]`, or calls `finishExperiment()` once exhausted (runs the Familiarity-Check/Post-Befragung before `showResults()` — see Datenerhebung above; `debugJumpToResults()` bypasses it and calls `showResults()` directly). The top progress bar/text and the "Bereit" overlay both display `orderPos+1 / levelOrder.length`, **not** the raw `CONFIG.levels` index. Debug-panel level navigation (`debugPrevLevel`/`debugNextLevel`) deliberately bypasses `levelOrder` and steps through raw config indices instead — this now means it can browse the **entire pool**, not just the session's 8, useful for QA/spot-checking the pool.

**Session preload (since 2026-08-26, Julian's testing found a mid-game "GeoJSON nicht geladen" error that forced him to abort a run):** `startShuffledExperiment()` now `await`s `preloadSessionLevels()` between `buildLevelOrder()` and the first `loadLevel()` call — fetches + verifies every session level's image and GeoJSON up front (`#preload-overlay`, progress text/bar) instead of discovering a broken/unreachable asset mid-playthrough. Each level gets up to 3 attempts (600ms backoff); a level that still fails is swapped for another not-yet-drawn pool index from `_fullShuffledPool` (the full shuffle `buildLevelOrder()` produces before slicing to `LEVELS_PER_SESSION`) — only once that replacement reserve is exhausted does the slot get dropped from `levelOrder` outright (session runs one level short rather than erroring). Successfully preloaded GeoJSON is cached in `_preloadedGeojson[levelIndex]`; `loadLevel()` uses that cache first and only falls back to its own fetch+error-banner path for levels that bypass preload entirely (the tutorial's silent `loadLevelSilent()`, and debug-panel raw-index navigation via `debugPrevLevel`/`debugNextLevel`, which can jump to any pool index on demand).

**Per level (`loadLevel(i)` in app.js):**
1. Loads the level's PNG + GeoJSON.
2. `buildZones()` reads each GeoJSON polygon ring as-is: coordinates are already `[fracX, fracY]` in `[0,1]×[0,1]` image-pixel space, computed server-side by `pipeline.py`'s `wgs84_geom_to_pixel_fraction()` against each level's own raster CRS. **Do not** reintroduce a WGS84/Web-Mercator-bounding-box mapping here — that was the actual bug fixed 2026-08-27 (see Memory `project_geogame_real_imagery`): source TIFs for the real pool are in EPSG:3035 (LAEA Europe), which is not north-aligned away from its projection center, so a plain WGS84-bbox → Web-Mercator-fraction interpolation produced hitboxes rotated/sheared by up to ~7° (>1000m) relative to the actual (unrotated) pixel grid. The fix reprojects hitbox polygons into each raster's native CRS before converting to fractions, since the pixel grid is a pure unrotated scale+translate in that CRS.
3. Shows a "Bereit" (ready) overlay with a 3-2-1 countdown; the timer (`startTimer()`) only starts once the countdown reaches 0 — image and labels stay hidden until then.
4. Drag-and-drop is native mouse events (`mousedown`/`mousemove`/`mouseup` on `document`), not HTML5 DnD — see `beginDrag`/`setupMouseEvents`. A magnifying "loupe" canvas and a pin cursor follow the mouse; both account for the image being letterboxed inside `#stage` if the container ratio differs from 4:3.
5. `handleStageDrop`/`handleTrashDrop` validate against `zones`, `absent`, and `absent_optional`; `checkLevelComplete` gates the "Weiter" button. Because zones can overlap slightly (see the WorldCover gap-fill note above), `handleStageDrop` collects **all** matching classes at the drop point into a `hitKlassen` Set rather than assuming a single match — any code consuming that set (e.g. `tutPracticeCheck`) must check membership (`.has(...)`), not just the first/only element.
6. Results accumulate in the `results` array (`{image, imgSrc, time, errors}`) and are shown/exportable (CSV/JSON) on the final results screen.

**Results screen:** clicking a row opens a full-screen image-preview lightbox (`#image-preview-modal`) showing that level's satellite image — scroll to zoom (cursor-centred), drag to pan, double-click to reset, ✕/Escape to close. See `openImagePreview`/`onPreviewWheel`/`onPreviewDragMove` in app.js.

**Debug mode:** press `D` in-experiment to toggle `#debug-panel` + a canvas overlay drawing every class's hitbox polygons (colour-coded, from `DEBUG_COLOURS`), with per-class checkboxes, raw-index level `‹ ›` navigation, and an "Aufgaben-Steuerung" section with two shortcuts for QA: **Nächste Aufgabe** (`debugSkipTask()` — force-advances the shuffled sequence regardless of whether the current level is actually solved) and **Zu den Resultaten** (`debugJumpToResults()` — jumps straight to the results screen) so testers don't have to solve every level by hand to reach the later parts of the flow.

**Current (real pool):** see "Real-imagery sourcing" above — acquire via the Satellitenbilder repo's `--profile game`, classify via this repo's `scripts/build_real_pool.py`, then commit the resulting `Bilder/EO_Bilder/IMG_*norm.png`, `Bilder/Hitboxes/IMG_*puf.geojson`, and `data/config.json`. No code changes needed for routine pool growth; only touch `ALL_LABELS` (in both `pipeline.py` and `build_real_pool.py`, plus `app.js`'s `CONFIG.labels` reliance) if the label set itself ever changes.

**Legacy (false-color, superseded):** drop TIFs into `input/`, run the old GUI pipeline (`.exe`/`.bat`) or the manual scripts, commit the resulting PNGs/GeoJSONs/config.json. Level ordering followed sorted TIF filenames (`B1`, `B2`, … by pipeline processing order).
